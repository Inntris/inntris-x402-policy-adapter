## Rules with passing tests but no implementation

Per the rule reference: _a rule with passing tests but no identifiable implementation, or with owner
`FACILITATOR`, is not enforced by Inntris regardless of the end-to-end result._ Three rows qualify.

- **SR2.** A10-F4 passes end to end against a compliant facilitator. `ABSENT` in the adapter; owner
  `FACILITATOR`. D1's permissive run shows the resource released.
- **SR5 settleability.** A7 passes end to end. `ABSENT`; owner `FACILITATOR`.
- **SR4.** No test passes, because E2 and E3 were never run. Recorded `NOT TESTED`, not `PASS`.

## Path divergence

Every `ENFORCED` or `RE-DERIVED` row above is library-path only. On the HTTP path the action arrives
pre-built and none of the derivation in `binding.ts` executes, so SR1's requirement binding in
particular reduces to trusting the caller's own hash. This is F-6.

## Ordering

Every enforced binding check is `POST_VERIFY` in the documented integration order. D1 measured it:
under a compliant facilitator, payee and amount swaps are rejected at `FACILITATOR_VERIFY` before
Inntris is consulted. D6's F-8 case shows the consequence — when the facilitator is unreachable, a
request Inntris could have rejected on its own fails as a transport exception with no verdict and no
reason code.

Only two checks are genuinely `PREFLIGHT`: the payload/requirements equality check at
`binding.ts:78`, and organisational policy evaluation itself, both of which run before any
facilitator call.
